# 3D 貨櫃裝載模擬系統

一個基於 Web 的互動式 3D 貨櫃裝載模擬與優化工具，使用極點啟發式演算法計算裝載配置，並提供即時 3D 視覺化呈現。整個系統為**單一 HTML 檔案**，開啟即用，無需安裝。

## 功能特色

### 🎯 核心功能

| 功能 | 說明 |
|------|------|
| **常用櫃型預設** | 20/40 呎標準櫃、40 呎高櫃、20/40 呎冷藏櫃，一鍵套用內尺寸 |
| **貨物清單輸入** | 表單式逐項輸入，含名稱、長寬高、數量、可堆疊/可旋轉 |
| **極點啟發式裝箱** | 垂直優先堆疊策略，同型貨物成直柱而非打平分層 |
| **多策略搜尋** | 4 種填充策略取最佳，長寬對調（120×100／100×120）結果保證一致 |
| **混合方位條帶** | 載具寬度非方位寬整數倍時混用兩種方位，冷藏櫃實測多裝 30 箱 |
| **多層堆疊與支撐檢查** | 底面需 ≥70% 被支撐；不可堆疊貨物上方零覆蓋 |
| **平均堆疊至櫃門** | 貨量少時自動降低堆疊高度、鋪滿櫃長，高度隨貨量增減 |
| **多載具配載** | 一票貨裝不完一個載具時自動開下一個，算出總共要幾個棧板／貨櫃 |
| **載具尺寸比較** | 棧板與 5 種櫃型同時試算，標出用得最少的那一種 |
| **逐一檢視載具** | 報表上每個載具可點選，直接在 3D 看該個載具的堆疊方式 |
| **最後一個載具鋪平** | 裝不滿的最後一個改以最低堆高重排，13 箱鋪成 5+4+4 而非 4+3+3+3 |
| **分層件數顯示** | 報表列出每層各幾箱，可對照 3D 畫面核對數量 |
| **剩餘空間快速評估** | 已裝載後，輸入新貨尺寸即時試算還能再裝幾箱 |
| **空櫃整櫃可裝計算** | 忽略清單，直接算單一外箱尺寸整櫃可裝幾箱 |
| **3D 即時視覺化** | 互動式 3D 場景，支援旋轉、縮放、平移；相機隨載具尺寸自動取景 |

### 🎨 視覺化特性

- **顏色區分**：同一種貨物同色，最多 8 色循環；未裝載為灰色、評估預覽為金色
- **狀態邊框**：正常（黑）、不可堆疊（橘紅）、無法裝載（紅）
- **貨物標籤**：每箱上方顯示名稱、狀態標記（不可堆疊／已旋轉）與尺寸
- **櫃外堆放**：無法裝入的貨物以灰色排列在貨櫃右側，一目了然；最多畫 40 件（`OUTSIDE_CAP`），避免數百件灰箱蓋掉整個畫面，剩餘件數由結果摘要以文字交代

### ⚙️ 進階選項

- **可堆疊設定**：指定哪些貨物允許其他貨物疊於其上
- **可旋轉設定**：允許貨物水平旋轉 90°（不倒置）
- **依清單順序裝載**：先裝清單前面的貨物（模擬既有貨先裝、新貨填剩餘空間）
- **平均堆疊至櫃門**：自動平均分佈、降低堆疊高度
- **標籤顯示控制**：一鍵開關貨物標籤
- **全域設定**：一次套用全部可堆疊／可旋轉

## 快速開始

### 1. 開啟程式

直接在瀏覽器中開啟 `container-loading-3d.html` 檔案。

### 2. 設定貨櫃尺寸

從「常用櫃型」下拉選單選擇預設，或於長／寬／高欄位自訂（單位：cm）。

**內建櫃型：**

| 櫃型 | 內尺寸 (長×寬×高 cm) |
|------|----------------------|
| 20 呎標準櫃 | 589 × 235 × 239 |
| 40 呎標準櫃 | 1203 × 235 × 239 |
| 40 呎高櫃 (HQ) | 1203 × 235 × 269 |
| 20 呎冷藏櫃 | 530 × 228 × 212 |
| 40 呎 HQ 冷藏櫃 | 1130 × 228 × 240 |

### 3. 輸入貨物清單

點「+ 新增貨物」，逐項填入名稱、長、寬、高、數量，並勾選是否可堆疊／可旋轉。也可點「載入範例數據」快速試用。

### 4. 計算裝載

點擊「🔄 計算裝載」，系統自動計算配置並以 3D 呈現，儀表板同步顯示裝載率與件數。

> **「計算裝載」只處理一個貨櫃。** 若把貨櫃尺寸填成棧板尺寸（例如 120×100×216）再按計算，得到的是「一個棧板裝得下幾件」——846 件會顯示成 `36/846`，其餘 810 件列為裝不進去。要問「整票貨需要幾個棧板」請改用「[多載具配載](#多載具配載整票貨要幾個棧板)」，該功能會回答 24 個棧板、每個 36 件（三長二寬六層）。結果摘要在有貨裝不進去時也會直接提示這一點。

> 使用「剩餘空間快速評估」時，金色預覽箱會一併計入上方統計。

### 剩餘空間快速評估

裝載完成後，於「裝箱快速評估」面板輸入新貨的長×寬×高（可勾可堆疊／可旋轉）：

- **📦 評估剩餘空間可再裝幾箱**：在目前裝載狀態上逐件試放，金色預覽顯示可再裝的箱數與體積。
- **🧮 計算空櫃整櫃可裝幾箱**：忽略貨物清單，直接計算整個空貨櫃能裝多少個該尺寸外箱。

金色箱子為評估預覽，重新計算裝載即清除。兩項結果都會附上**分層件數**（例如 `分 5 層：70 + 70 + 70 + 70 + 70 箱`），因為實心貨堆從外面只看得到表面，光看 3D 畫面很容易少算一整排。

### 多載具配載（整票貨要幾個棧板）

當一票貨裝不完單一載具時，於「多載具配載」面板計算需要幾個載具才裝得完。同一票貨使用同一種尺寸的載具。

1. **勾選候選載具**：清單含 8 個候選 —— 棧板 A（120×100）、棧板 B（120×80）長寬可直接改成任何自訂尺寸；5 種櫃型（20 呎／40 呎／40 呎高櫃／20 呎冷藏／40 呎 HQ 冷藏）；以及「上方自訂貨櫃尺寸」。棧板與貨櫃可同時勾選、放在同一張報表比較，因此**「裝不下的貨該送哪種櫃」與「要幾個棧板」是同一次計算回答的**。
2. **填入堆貨高度**：高度依客戶要求與海運／空運而異，故不設預設值，每票貨自行輸入。此欄位**只套用於棧板**，是棧板上方的淨堆貨高度，棧板本身 12.5 cm 不計入；貨櫃候選一律使用它自己的高度。
3. **按下計算**：各候選尺寸分別試算，報表列出每個載具裝幾件、裝載率多少。

排名規則：能把整票貨裝完者優先 → 需要的載具數少者 → 總佔地面積小者。第一名標上 🏆。

**實際堆高**：報表顯示的是箱頂的真實高度，不是輸入的高度上限。例如高度上限 180 cm、貨物高 40 cm 時，實際只堆得到 4 層 160 cm，連棧板總高為 172.5 cm（而非 180 + 12.5）。各載具高度不同時顯示為範圍。

**逐一檢視每個載具**：報表上每個載具都是一枚可點的編號籌碼（`#1 20件 71%`），點下去就在 3D 畫出那一個 —— 要看第 17 個棧板怎麼堆，點 `#17` 即可。滑鼠停留可看該載具的完整數字。按「🔄 計算裝載」切回貨櫃視圖。

**配載採「裝滿為先」**：依序把每個載具裝滿，最後一個裝剩下的。這是實際裝櫃作業的做法，也才能正確回答「最少要幾個」。因此此功能不套用「平均堆疊至櫃門」（該選項是為貨櫃內的重心分布設計的）。

**最後一個載具會橫向鋪平**：裝不滿的那一個改以「件數不變下的最低堆高」重排，剩 13 箱會鋪成 5+4+4 三層（堆高 120 cm），而不是堆成 4+3+3+3 的四層高柱（堆高 160 cm）。因此報表的「實際堆高」會顯示成範圍，例如 `實際堆高 120~160 cm`。

報表最後一行會列出目前 3D 顯示中的載具是**怎麼疊的**，例如 `13 件，堆高 120 cm，分 3 層：5 + 4 + 4 箱` —— 實心貨堆從外面只看得到表面，光看 3D 畫面很容易少算一整排，有這行數字才能核對。

任何擺法都放不下該載具的貨物會單獨列為「無法裝入」，並在 3D 中以灰色顯示於載具右側。

## 核心演算法

### 極點啟發式（Extreme-Point Heuristic）＋垂直優先

系統採用極點啟發式裝箱，核心概念：**由已放置箱子的邊界產生候選位置，貨物落下後取靜止高度，選出最佳位置放置**。

#### 演算法流程

```
1. 貨物排序
   ├── 預設：依體積由大到小（同型貨物連續處理）
   └── 「依清單順序裝載」：保持輸入順序

2. 對每件貨物：
   ├── 產生候選欄位（已放箱子的 X 邊界 × Z 邊界網格）
   ├── 對每個候選 × 每個水平方向（原始／旋轉90°）：
   │   ├── 計算落下後的靜止高度（footprint 範圍取箱頂最大值）
   │   ├── 檢查：櫃內、有支撐、不壓在不可堆疊箱上
   │   └── 以 (x, z, y) 最小者為最佳（先內、先橫、同柱疊滿才換位）
   └── 放置最佳位置，或標記為無法裝載

3. 以完整策略集合（4 基本 + 最多 2 條帶）各跑一次上述流程，
   取裝載件數最多者；有策略全裝完就提早收工（見下兩節）

4.（可選）平均堆疊：見下節
```

**垂直優先** `(x, z, y)` 評分，讓同一直柱疊滿到頂才移往下一位置，如同實際裝櫃一面牆一面牆裝，同型貨物自然成直柱，而非打平分層。

#### 多策略搜尋（長寬對調對稱性）

貪婪法對「先填哪個軸」與「先試哪個方位」極度敏感。單一策略會讓物理上等價的問題算出不同答案 —— 實測 45.4×35.6×36.8 的貨在 120×100×135 只裝 12 件，長寬對調成 100×120×135 卻裝得下 18 件（正解是 35.6 沿長排 3 列、45.4 沿寬排 2 列，每層 6 箱 × 3 層）。

```javascript
const PACK_STRATEGIES = [
    { zFirst: false, rotFirst: false },   // x 軸優先、非旋轉方位優先
    { zFirst: false, rotFirst: true  },
    { zFirst: true,  rotFirst: false },
    { zFirst: true,  rotFirst: true  }
];
```

- `zFirst` — 位置評分的字典序由 `(x, z, y)` 換成 `(z, x, y)`
- `rotFirst` — 方位候選順序反轉，優先嘗試旋轉 90° 的擺法

這 4 個策略在 x↔z 對調下**兩兩互為配對**（0↔3、1↔2），構成封閉集合。因此「取件數最多者」使 `f(L, W) = f(W, L)` 成為結構上的保證，而非調參數湊出來的結果。此性質在貨物皆可旋轉時嚴格成立。

`packCargoBest` 是此搜尋的入口，`calculateLoading`／`calculateFullCapacity`／`evaluateRemaining`／`packMultiCarrier` 全部走同一條路（`allStrategies()`）。一旦某個策略把貨全裝完就收工 —— 已經沒有更多可裝，其餘策略不可能更好。

#### 混合方位條帶（Band Strategy）

上面 4 個基本策略有一個共同盲點：**同一個位置的兩種方位分數必然相同**，永遠由同一個方位勝出，於是整個載具只會出現單一方位。當載具寬度不是方位寬度的整數倍時，這會白白浪費一條邊。

以 49.8×35.8 的外箱放進寬 228 cm 的 40 呎 HQ 冷藏櫃為例：

| 配置 | 每層件數 |
|------|---------|
| 單一方位 6 條（寬 35.8）× 22 箱 | 132 |
| **混合 2 條（寬 35.8）+ 3 條（寬 49.8）** | **2×22 + 3×31 = 137** |

`bandSplitAt()` 把這件事化簡成一維背包（兩種寬度填一條線段，直接掃遍所有組合即為最佳解），回傳一個**分割座標**：座標之前只准不旋轉、之後只准旋轉。`bandStrategies()` 對兩個軸各產生一個策略，這兩個在 x↔z 對調下互為配對，因此對稱性的封閉集合性質不變。

只有「混合嚴格優於任一單一方位」時才產生策略，否則省下一次完整試裝。實測提升：

| 貨物 | 載具 | 修正前 | 修正後 |
|------|------|-------|-------|
| 49.8×35.8×36 | 40 呎 HQ 冷藏櫃 | 792 | **822** |
| 49.8×35.8×36 | 20 呎冷藏櫃 | 300 | **310** |
| 45.6×37.8×36.8 | 40 呎標準櫃 | 936 | **966** |
| 45.6×37.8×36.8 | 40 呎高櫃 | 1092 | **1127** |

#### 支撐與堆疊規則

```javascript
// 1. 貼地必然成立
// 2. 否則底面需 >= 70% 壓在「可堆疊」箱子的頂面上
// 3. 不可堆疊箱「上方零覆蓋」：任何高度只要垂直投影重疊即拒絕
```

#### 平均堆疊至櫃門（Spread）

貨量不足一櫃時，避免貨物全堆在前段、櫃門端空一大截：

```
1. 先以滿高度裝載，取得可裝件數 target
2. 枚舉「貨物高度能組成的精確塔高」作為候選高度上限（BFS，不取整）
3. 對每個候選上限實際試裝，取「件數最多、上限最低」者
   → 完全不依賴單調性假設（垂直優先貪婪法的件數對高度上限非單調）
4. 候選過多時退回均勻網格掃描
```

結果：貨物以較低高度從櫃底鋪滿到櫃門，堆疊高度隨貨量自動增減。

> **與多策略搜尋的取捨**：高度上限掃描沿用第 1 步選出的那一個策略，不對每個上限重跑 4 策略。若全跑（25 個上限 × 4 策略 = 100 次裝箱），1500 件貨會算到瀏覽器凍結（實測約 68 秒）。候選高度集合只由貨物高度決定、與長寬無關，因此長寬對調的對稱性仍然成立。

#### 多載具配載（Multi-carrier）

```
1. 先濾掉「空載具都放不下」的貨物 → oversized
2. while 還有貨：
   ├── packCargoBest(剩餘貨物, 載具)
   ├── 這輪裝進去的成為一個載具
   └── 沒裝進去的成為下一輪的輸入
```

第 1 步是關鍵：濾掉之後，剩下的每一件都保證能單獨放進空載具，**每一輪必然至少裝進 1 件**，迴圈因此必然終止。不需要人為的載具數上限，也不需要「這輪裝了 0 件就 break」的補丁分支 —— 把特殊情況消滅在資料層，而不是用條件判斷去補。

#### 最後一個載具橫向鋪平（packLowestStack）

前面的載具「裝滿為先」（要回答的是「最少要幾個載具」），但最後一個通常裝不滿。若沿用同一套垂直優先規則，剩下的貨會堆成一根孤零零的高柱 —— 實務上沒人這樣疊。

`packLowestStack()` 在**一件都不能少**的前提下把貨堆到最低：由低往高試候選塔高（`reachableStackHeights`），第一個能全裝的就是答案。

```
120×100 棧板、56.8×33.6×40 的貨、剩 13 箱
  修正前：4 + 3 + 3 + 3 → 堆高 160 cm（四層高柱）
  修正後：5 + 4 + 4     → 堆高 120 cm（三層鋪平）
```

- 起點用體積下界剪枝（貨物體積 ÷ 載具底面積），跳過必然裝不完的低塔高
- 同型貨物的候選塔高只有「層數」那幾個，實際只會試 1～3 次
- 每個塔高都重跑完整策略集合（不像 `packCargoSpread` 沿用單一策略）—— 「每層放幾箱」正是策略之間差最多的地方
- 件數保證不變，因此絕不會讓載具數量變多

## 效能考量

### 大量貨物處理

40 呎櫃、`packCargoBest`（含策略搜尋）實測：

| 貨物數量 | 預期效能 |
|----------|----------|
| < 500 | 流暢（毫秒級） |
| 500-1000 | 良好（< 0.5 秒） |
| 1000-1500 | 可接受（約 3～4 秒） |
| > 1500 | 超過件數上限，需減量 |

多載具配載因單一棧板容納件數少、候選欄位極少，速度遠快於整櫃計算（1000 件分裝 56 個棧板約 0.3 秒）。7 個候選載具同時比較時，846 件約 4 秒、1500 件約 19 秒。

- 展開後件數上限 `MAX_PIECES = 1500`，避免瀏覽器凍結。
- 候選欄位網格上限 `GRID_CAP = 10000`，超過時退回箱角欄位以維持速度。
- 策略搜尋使裝箱耗時約為單策略的 N 倍（N = 4～6）；但「有策略全裝完就收工」讓能全裝的情況只跑 1 次，846 件在 40 呎櫃因此由 1.0 秒降到 0.18 秒。
- 平均堆疊刻意不與策略搜尋相乘（見核心演算法一節）。
- 所有耗時運算都經 `runBusy()` 包裝，按鈕會先變成「⏳ 計算中…」再開始算。

### 優化建議

1. **關閉標籤**：大量貨物時關閉貨物標籤可提升渲染效能。
2. **數量分組**：相同尺寸貨物以「數量」欄位輸入，勿逐件新增。

## 限制與注意事項

1. **僅支援長方體**：不支援不規則形狀貨物。
2. **無重量考量**：不計算貨物重量與重心。
3. **單一貨櫃**：每次計算僅處理一個貨櫃。
4. **旋轉限制**：僅水平旋轉 90°，不支援倒置。
5. **啟發式解**：為快速啟發式而非全域最優；實際裝櫃若允許人工塞縫，件數可能略有出入。
6. **需連網載入**：Three.js 由 CDN 載入，離線會顯示錯誤提示。
